# Authenticated gRPC transport

The agent executes commands received over its gRPC stream. Encryption without
verifying the server identity is not enough: an impostor server could issue
commands or collect enrollment/reconnection tokens. TLS is therefore the default
for both the engine gRPC server and every agent entrypoint.

## Configuration

| Variable | Process | Meaning |
| --- | --- | --- |
| `GRPC_TRANSPORT` | Both | `tls` (also the default when unset). Only other value: `insecure-loopback`, for isolated local development. |
| `GRPC_TLS_CERT_FILE` | Server | Required PEM server certificate, followed by any intermediate certificates. |
| `GRPC_TLS_KEY_FILE` | Server | Required matching PEM private key. Protect with service-account-only read access. |
| `GRPC_TLS_CA_FILE` | Agent | Optional PEM CA trust bundle. When specified, replaces system trust roots. Otherwise uses OS roots. |
| `GRPC_TLS_SERVER_NAME` | Agent | Optional expected server DNS name when connecting using a different address. Default verifies the hostname/IP from `SERVER_ADDRESS`. This does not disable certificate verification. |

Minimum protocol: TLS 1.2. Certificate chain, expiry and hostname/IP SAN are
verified before the stream or authentication token is sent. No skip-verification
option, automatic trust-on-first-use, self-signed certificate generation, or
plaintext retry is provided. Unknown transport values and unreadable/invalid
files fail closed. The server checks TLS configuration before initializing its
other services and again before listening.

Example server (provision certificates through your existing PKI first):

```sh
SERVER_ADDRESS=:50051 \
GRPC_TLS_CERT_FILE=/etc/sirius/tls/server-chain.pem \
GRPC_TLS_KEY_FILE=/etc/sirius/tls/server-key.pem \
./sirius-server
```

Example agent with a private CA:

```sh
SERVER_ADDRESS=engine.example.com:50051 \
GRPC_TLS_CA_FILE=/etc/sirius/tls/ca.pem \
./sirius-agent
```

For an IP connection to a certificate issued for a DNS name, also set
`GRPC_TLS_SERVER_NAME=engine.example.com`. Obtain the CA bundle and expected
identity through a trusted administrative channel, not from an unauthenticated
server. Never copy the server private key to agents.

## Upgrade from plaintext releases

This is an intentional compatibility break: old plaintext agents cannot connect
to the TLS server, and updated agents will not connect to old plaintext servers.
Existing agent IDs and enrollment tokens remain valid; transport security does
not require resetting them. Plan a coordinated maintenance window:

1. Issue a server certificate for the exact DNS name/IP agents will verify. Make
   its chain and private key available only to the server service account. Do
   not commit private keys or put them in container images.
2. Distribute the trusted public CA bundle to agents if using a private CA.
   Prepare the new environment variables and read-only certificate mounts in
   your service/container definitions. Existing deployment examples do not
   automatically provision TLS.
3. Upgrade the server and agents together and restart them with the configured
   files. Validate a representative agent enrollment, reconnection and harmless
   status command in staging first. A maintenance window avoids mixed-version
   disruption. Do not reopen a network plaintext listener to accommodate older
   agents.
4. Confirm the certificate name matches the address (or explicitly configured
   expected name). A trust, expiry, or name error must be fixed at the source,
   not bypassed by disabling verification.

For the Sirius Compose deployment, use the base configuration and follow
`Sirius/documentation/GRPC-TLS.md`. It mounts operator-provided files using the
**host-path** variables `SIRIUS_GRPC_TLS_CERT_FILE` and
`SIRIUS_GRPC_TLS_KEY_FILE`; exporting the process-level `GRPC_TLS_*` variables on
the Docker host alone does not configure container mounts. No TLS credentials
are generated by the installer.

There is no dual TLS/plaintext listener or automatic downgrade. Rollback to an
old plaintext release restores the vulnerability and is not a secure migration
strategy. For a rolling migration, use an independently provisioned TLS endpoint
and a documented deployment plan; this source change does not create or trust a
proxy automatically. Any termination proxy must protect its backend path too.

For certificate rotation, replace files and restart the affected process. Root
CA rollover can use a bundle containing both old and new trusted roots, then
remove the retired root after all server certificates have changed. Certificate
files are loaded during startup, not watched live.

## Explicit local-development exception

For isolated same-machine development only, both processes may set:

```sh
GRPC_TRANSPORT=insecure-loopback SERVER_ADDRESS=127.0.0.1:50051
```

Literal IPv4/IPv6 loopback addresses and numeric ports are required. Wildcard
binds, remote addresses, DNS names (including `localhost`), and gRPC resolver
URIs are rejected. The client disables proxy routing for this mode. Both sides
log a plaintext warning; combining this mode with TLS settings is rejected.
This exception offers no protection from other local processes and is not for
production, remote agents, or connections between containers. Do not use
production tokens or data in local plaintext tests.

## Scope

TLS authenticates the server and protects the gRPC stream. Agent authentication
continues to use the existing enrollment/token mechanism; this change does not
introduce mTLS or change enrollment approval policy. It does not secure separate
REST API, Valkey or message-queue connections. Those require their own transport
and authorization controls.

## Tests

`go test -race ./internal/config ./internal/agent ./internal/server` covers secure
defaults, invalid files, local-only plaintext restrictions, successful verified
streams, untrusted/expired/mismatched certificates, and both protocol mismatch
directions. TLS tests generate synthetic keys in temporary test directories and
use ephemeral loopback listeners. They never connect to a live agent or service.
